# Recall-DSA — Frontend Design & Specification (v1)

This is the living reference for frontend/UI/UX decisions: visual identity (colors, typography), page-by-page specs, decided UX behavior, open questions, and implementation conventions for the Go `html/template` + htmx frontend. SPEC.md and CLAUDE.md own the backend/product spec; this file owns how it looks, feels, and is built on the frontend.

**Read this before making any visual or UX change**, the same way SPEC.md is read before a backend/architecture change. When a decision gets made in discussion, it belongs here — not just in chat history.

## Stack (from CLAUDE.md)

- Server-rendered HTML via Go's `html/template` — no client-side framework
- htmx for interactivity — attributes only, no build pipeline, no npm, no React/Vue, no bundler
- htmx and fonts self-hosted via `go:embed` (`internal/httpapi/assets.go`) — no CDN dependency
- CSS: plain inline `<style>` in the shared layout template; no CSS framework or preprocessor
- One Go binary serves both API and HTML

## Current build status

- **Step 4 (HTTP handlers)** — complete: the full workflow (dashboard, due queue, grading, add/edit/delete problems, library, topics) is built.
- **Step 5 (htmx templates/UI)** — visual identity, theming, htmx grading, and a full mockup-driven pass over Home/Due/Topics/Add Problem/Library are all built (see "Decided UX facts"). Bulk Import remains deliberately deferred (SPEC.md §9, CLAUDE.md build-order step 6).

## Visual identity

- **Colors**: three CSS-variable themes, switched via a `[data-theme]` attribute on `<html>`, driven by a cookie plus a live JS toggle (no page reload): **Rose Pine Dawn** (light, default), **Rose Pine Moon** (dark), and **Nord** (custom — Nord has no native names for these roles, so it's mapped onto Rose Pine's role shape: nord0-3/Polar Night → base/surface/overlay/muted, nord4/6/Snow Storm → subtle/text, nord8-10/Frost → pine/foam/iris, nord11-13/15/Aurora → love/gold/rose). A two-tier token system keeps component CSS pointed at **semantic** names, never raw palette values:
  - Raw palette (per theme): `--color-base`, `--color-surface`, `--color-overlay`, `--color-muted`, `--color-subtle`, `--color-text`, `--color-love`, `--color-gold`, `--color-rose`, `--color-pine`, `--color-foam`, `--color-iris`, `--color-highlight-low/med/high`.
  - Semantic layer (defined once, unconditionally): `--bg`, `--surface-bg`, `--text`, `--muted-text`, `--border`, `--link`, `--danger`, `--tag-bg`, `--tag-accent`, `--grade-failed/hard/good/easy`, `--difficulty-easy/medium/hard`.
- **Typography**: IBM Plex Sans (primary) / IBM Plex Mono (code, URLs, slugs, technical identifiers only), self-hosted via `go:embed`. Restrained type scale: page title (`h1`) 28px/600, section heading (`h2`) 20px/600, problem title 16px/500, body 15px/400, meta text 13px/400, small labels (`th`/`label`) 12px/500. Don't add sizes/weights beyond this scale.
- **Spacing/layout scale**: ad hoc rem values, no formal scale — not revisited; not a pain point so far.
- **Iconography**: none. Not wanted (kept the app text-first; several mockups included icons/logos that were deliberately not adopted — see "Decided UX facts" #11).

## Decided UX facts

1. **Home (`/`) is a pure-glance dashboard, not an action surface.** It shows a due count and a compact, read-only due list (title/topics/next-review-date — no grade buttons, no Upcoming section). Every row's title still links out to LeetCode as normal. Clicking through (a "Go to Due →" link) is the only path from Home into actually grading anything. Rationale: avoids two places that can both mutate review state, and matches the mental model of "Home = orientation, `/due` = where you act" — decided explicitly over the alternative (keeping Home's table gradable) after weighing both.
2. **`/due` is now the single place that shows both Due and Upcoming, topic-filterable together.** One topic dropdown drives both sections — selecting "Graphs" filters Due-Graphs and Upcoming-Graphs at once, via `RecommendUpcoming` accepting the same topic filter `RecommendDue` does.
3. **Upcoming items are view-only** (no grade buttons) — grading before a problem is actually due would inflate ease/interval on a false signal, undermining genuine retention testing. This is a UI-level choice only; the backend (`RecordReview`) does not enforce a due-date check.
4. **Upcoming lookahead window is 7 days.**
5. **On `/due`, Upcoming is structurally distinct from Due**: both sections visible on one page (no tabs, no side-by-side columns — stacked, Due on top), Upcoming rendered with a muted/de-emphasized treatment (via the `--surface-bg`/`--muted-text` semantic tokens above) and no action buttons.
6. The persistent top nav (Due / Library / Add Problem / Topics) is treated as sufficient "quick links" — Home does not duplicate them as separate cards.
7. Every outbound LeetCode link uses **named-window targeting** (`target="leetcode"`), so clicking through always reuses one browser tab (SPEC.md §7) — never omit this on a page that links to a problem.
8. Destructive actions (delete problem, delete topic) use a native `confirm()` guard — a small, deliberate exception to the htmx-first approach below, since a confirm dialog isn't something htmx does.
9. **One shared error-page template covers 400/404/500** (routed through the existing `renderError` helper, plus replacing the raw `http.NotFound` call in the edit-problem handler) — same layout, status-specific heading. Shows the actual underlying error text (e.g. `service: invalid difficulty "Extreme"`), not a generic "something went wrong" message — reasonable since this is a single-user, self-hosted tool (SPEC.md §10) where the user is also the one who'd debug it. 422s (form validation failures) are unaffected — those already re-render the actual form with an inline error so input isn't lost, which is better UX than a separate error page.
10. **Nav and buttons are styled, not bare browser chrome.** Every plain `<button>` gets a default look via a single `button { ... }` rule (background `--link`, `--color-base` text) — no per-template classing needed, since more specific existing classes (`.grade-btn`, `.theme-switcher a`) already out-specificity it and override where they need their own colors. Destructive buttons (delete problem, delete topic) get `.btn-danger` (`--danger` background). Standalone action links get `.btn-link` to look like a button (Home's "Go to Due →", Library's page-title badge). Nav links are pill-styled (`padding`/`border-radius`, hover state) instead of default underlined text, and the current page is highlighted (`.nav-active`) the same way the theme switcher already highlights the active theme — computed centrally in `internal/httpapi/theme.go`'s `navActiveFor(path)` and threaded through a `layoutData{Theme, Active, DueCount, Page}` wrapper, so no per-page view-data type needs an `Active` field of its own.
11. **Home is enriched with lightweight, purely-descriptive stats**, following review of Stitch mockups: a Total Tracked count, a Difficulty Split readout, and a "Review Load" sidebar (upcoming reviews grouped by exact day-offset, next 5 days, zero-filled — `Service.UpcomingByDay`, distinct from `/due`'s flat 7-day Upcoming list). Deliberately **not** built: Average Retention % (undefined semantics — real design work, not just a query), current streak, and overall grade distribution (both explicitly deferred by the user until "after the project is fully complete"). The mockups' "Study Advice" coaching card (a hardcoded tip + target daily cadence) was rejected as conflicting with SPEC.md's no-curriculum-guidance stance — replaced with a motivational quote card instead (`internal/httpapi/quotes.go`; **quote list not yet supplied by the user** — the card renders nothing until it is). Also rejected as mockup-tool artifacts, not real features, across every round: a "Simulate empty queue" button, a user/profile icon (no auth/multi-tenancy exists or is wanted — SPEC.md §13), an "AlgoRepeat" rebrand (staying Recall-DSA), and fabricated footer text like "SQLite WASM local storage" / "FSRS-4.5 engine" (this app is server-side SQLite, not client-side WASM, and deliberately uses SM-2, not FSRS — SPEC.md §13).
12. **A global "N due today" pill lives in the nav on every page** (`layoutData.DueCount`, computed centrally in `render`/`renderError`/`renderFormError` via `Service.CountDue` — same pattern as `Theme`/`Active`). This is the one mockup artifact that got reconsidered rather than dropped outright across rounds — the user wanted it kept, just applied globally rather than appearing once. It fails open to 0 on a query error rather than breaking a page render, since it's decorative, not the actionable Due list (`RecommendDue` remains that).
13. **Topics page is built around per-topic problem counts** (`Service.TopicCounts`, a LEFT JOIN so zero-problem topics still appear): the main table has an Active Problems column (count + bar, width relative to the busiest topic), header stats (Total Topics, Mapped Problems), and a **Topic Distribution** section below the table (bars + percentages, sorted by count descending) — this was the mockup's "Curriculum Distribution" / "SM-2 load" section, deliberately relabeled: it's a plain per-topic count breakdown, unrelated to SM-2 intervals, and the original label was misleading.
14. **Add Problem's Difficulty and First Grade fields are visual pills/cards instead of `<select>`s** — same form field names/values, so no handler change was needed, only the input markup (radio buttons styled via `:has(input:checked)`, same pattern as `.topic-chip`). First Grade card intervals are the real scheduler constants (`internal/scheduler/scheduler.go`), corrected against a mockup that had them wrong: Failed = tomorrow (1 day), **Hard = 3 days**, **Good = 5 days**, Easy = 7 days. Edit Problem's difficulty field uses the same pills via a shared `partials/difficulty-picker.html` partial, closing what was originally a known inconsistency (Edit kept a plain `<select>` after Add got pills).
15. **The topic picker (`partials/topic-picker.html`) intentionally stays a checkbox-chip list with a filter box**, not a searched/typed tag-input some mockups show. The user prefers being able to see and tick from the full list of existing topics rather than needing to recall and type a topic name — a standing preference for topic selection generally, not a one-off exception for any single page.
16. **A small, restrained set of motion was added**, all gated behind `@media (prefers-reduced-motion: no-preference)` so motion-sensitive visitors keep the previous instant behavior: (a) a 1s cross-fade on every themed color property (`body, body *`) so switching Light/Dark/Nord fades instead of snapping; (b) a 250ms hover transition on buttons/links/nav/theme-switcher/grade buttons; (c) the htmx grade-confirmation badge fades in via htmx's own `swap:0.2s settle:0.2s` timing modifier plus a `.grade-cell` opacity transition, instead of popping in instantly; (d) the Topics page's bars (`.topic-count-bar-fill`) grow from 0 to their rendered width once on page load via a `@keyframes grow-bar` animation.
17. **Theme switching is a live, no-reload attribute toggle, not a full page navigation.** The original redirect-based switch (`GET /theme/{name}` → set cookie → `303` back to the referring page) fundamentally couldn't produce a real cross-fade: a full page reload tears the old DOM down before the new one exists, so there's no persisting element for a color transition to fade *from* — what looked like a "shake" was actually the fresh page's elements settling into their colors at slightly different moments during parsing, which got worse (not better) as the fade duration increased. Fixed by a small inline script in `layout.html` that intercepts theme-switcher clicks, sets `data-theme` on `<html>` directly (a real live change the transition CSS can actually animate), and persists the cookie via a background `fetch` carrying an `X-Theme-Live: true` header. `handleSetTheme` branches on that header — `204 No Content` for the live-JS path, the original `303` redirect otherwise — so theme switching still works with JS disabled, just without the live fade (same progressive-enhancement pattern as htmx grading's `HX-Request` branch).
18. **Library gained a real feature set, not just a visual pass**: header stats (Total Tracked, Difficulty Split — same components as Home), an SRS Interval column and a color-coded Next Review status column (Overdue Nd / Today (Due) / Tomorrow / In N days, computed in Go against `Service.Today()`, not string-parsed in the template), title-only free-text search, a sort dropdown (Next Review default / Title / Difficulty), and pagination (10/25/50 rows, Prev/Next + a "Showing X–Y of N" label, with an out-of-range `page` clamping to the last page rather than showing a nonsensical range). Backed by `Service.ListLibrary` (`internal/service/library.go`), which joins `review_state` — safe as an inner join since every problem always has one from creation (`AddProblem` requires a first grade). A `/` keyboard shortcut focuses the search box. Rejected from the mockup: an "Export JSON" button (new scope beyond SPEC.md's CSV Bulk Import, deferred), the usual "AlgoRepeat"/profile-icon/fabricated-footer artifacts (see #11), and the mockup's "Scheduled"/"New (0d)" status (doesn't apply here — no problem is ever "unscheduled").
19. **Topic input UX** was resolved by replacing the free-text comma field with the checkbox-chip picker (`partials/topic-picker.html`, shared by Add and Edit, see #15): every known topic renders as a clickable pill (`.topic-chip`, toggled via `:has(input:checked)`), with a small vanilla-JS filter-as-you-type since the topic list is too large to browse flat. A small separate field remains for genuinely new tags. The topic seed itself grew from 18 to 35 (NeetCode 150's categories kept verbatim + 17 LeetCode tags for concepts NC150 has no category for — `internal/db/schema.sql`), fixing the underlying near-duplicate-tag risk by making existing topics clickable instead of retyped from memory.

## Frontend implementation conventions

Parallel to CLAUDE.md's "Go Guidelines" — these govern template/HTML/CSS/htmx work specifically.

- Templates live in `internal/httpapi/templates/`: one file per page, plus `layout.html` (shared chrome) and `partials/` (reusable fragments, e.g. `due-table.html`).
- Each page is parsed as its own isolated `*template.Template` (`layout.html` + all partials + that one page file) — **never** parse all page files together. `{{define "content"}}` (and any other shared block name) collides across pages within a single template set; see the doc comment on `pageTemplates` in `internal/httpapi/templates.go`.
- htmx is in use (`/due`'s grading), self-hosted via `go:embed` (`internal/httpapi/assets.go`) alongside the fonts — not a CDN script tag. Keep any future interactivity to this same htmx-first, no-build-pipeline approach rather than reaching for a framework. Small inline vanilla-JS (the `confirm()` destructive-action guards, the topic-picker's filter-as-you-type, the theme-switcher's live toggle, Library's `/`-to-search shortcut) stays fine for things htmx doesn't fit.
- No CSS framework, no build step — hand-written CSS in `layout.html`'s `<style>` block.
- Keep forms working without JS wherever possible — htmx should be an *enhancement* layer, not a hard requirement for basic functionality, mirroring SPEC.md's "never a hard dependency" philosophy elsewhere (e.g. §9's optional LeetCode metadata lookup).
- View-only arithmetic/derived display fields (bar widths, percentages, status labels) are computed in Go and passed to the template as plain fields — never computed inline in `html/template`, which has no arithmetic. See `topics.go`'s `topicRow`/`distributionRow` and `library.go`'s `libraryRow`/`statusLabel`/`statusClass` for the pattern.
- When asked to make a frontend/visual change, check this file's "Visual identity" and "Decided UX facts" sections first — don't invent a color, font, or UX behavior that contradicts (or should have been recorded in) this doc.
